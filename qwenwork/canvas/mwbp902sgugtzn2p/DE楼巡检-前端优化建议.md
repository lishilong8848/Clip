## DE楼巡检（日常巡检）前端优化建议

分析对象：`bin/lan_bitable_template_portal/frontend/src/components/` 下的 `DailyInspectionPage.vue`（1192 行）、`DailyInspectionWorkbook.vue`（619 行）、`DailyInspectionHistory.vue`（416 行）、`inspectionCellVisibility.ts`，以及后端 `daily_inspection.py` 的接口语义。

已排除近 20 次提交中已经做过的优化：权限与楼栋隔离、原表映射唯一性核验、双层乐观锁（设备级 `revision` + 轮次级 `review_version`）、参数延迟映射与免填区、导出样式/插图保真、人工状态跨轮继承、定时取数与批次匹配、自动收尾重试、摘要/单表按需加载、横竖屏适配。下面只列真正的空白点。

---

## 0. 一个必须先处理的前提：当前生效的界面只有工作簿

`DailyInspectionPage.vue:305` 定义了 `const sheetOpen = ref(true)`，全文件**没有任何一处对它赋值**（仅 `:42` 的 `v-if` 和 `:1011` 的 `back()` 读取它）。而 `:42` 是：

```
<template v-if="state && !historyOpen && !sheetOpen">
```

`sheetOpen` 恒为 `true`，意味着 **`:42`–`:215` 这一整段（174 行模板）永久不渲染**。这段里包含：

| 死代码 | 位置 | 原本承载的能力 |
|---|---|---|
| 查看楼栋 D/E 切换 | `:43-49` | 已被工作簿 `:14` 的楼栋下拉替代 |
| 专业预览 + 设备卡片读数 | `:68-101` | 开始巡检前按楼层/房间浏览参考读数 |
| **按专业分别确认的页脚** | `:194-207` | `confirm-profession` 逐个专业签字 |
| 楼层/房间导航、搜索框、专业筛选、只看缺失 | `:126-139` | 卡片式核对的导航与过滤 |
| 设备排序弹窗 | `:216-242` | `/api/daily-inspection/order` 的设备级排序 |
| 最近归档列表 | `:209-214` | 历史轮次快捷入口 |

**直接后果**：后端完整实现的「按专业分别确认」（`confirm-profession`、`profession_confirmations`、`profession_versions`）在当前 UI 里**没有任何入口**。实际生效的归档路径只有工作簿页脚的 `submit()`（`Workbook:479-481`，带 `sheet_workflow:true`），后端在该分支会**自动为所有已选专业写入确认**（`daily_inspection.py:1798-1808`）。

也就是说：**「两人各管一个专业、各自签字确认」这个业务模型，目前在界面上走不通。**

同时 `DailyInspectionSheet.vue`（181 行）无任何 import，也是孤立文件；`check-inspection-navigation.mjs` 仍在断言 `.inspection-device` 选择器，测的是已不渲染的界面。

**建议**：先做一次「界面事实基线」清理——明确保留工作簿为唯一编辑面，把死代码移入独立分支或删除，同步修正 e2e 脚本；或者反过来，把设备卡片视图作为「快速核对模式」重新接回。**这个决策必须先做**，否则后续任何优化都可能加在不会渲染的代码上。

**收益**：减少约 500 行无效代码与打包体积；消除「功能存在但点不到」的认知偏差；后续优化有确定的落点。

## 1. 交互流程

### 1.1 工具栏承载了 9 类控件，缺少「我在哪 / 还剩什么」的状态区

`Workbook:12-41` 的 `.book-tools` + `.book-status` + `.round-tabs` 里挤着：楼栋、日期、刷新、导出、专业筛选、工作表搜索、表格设置、开始巡检插槽（`:29`）、排序读取错误、图例、保存状态、正在编辑地址、重试保存、核对最新数据、四个轮次时点。全部用 `flex-wrap` 自然换行，没有分组层级。

**建议**：把工具栏拆成三层固定区域：
- **上下文层**（楼栋 / 日期 / 轮次时点）——低频切换，收进一个紧凑的「当前班次」胶囊；
- **导航层**（专业筛选 / 工作表切换 / 排序）——高频，保持常驻；
- **状态层**（保存状态 / 进度 / 提交）——做成吸底常驻条，永远可见。

**收益**：高频操作不再被低频控件挤到换行后不可见；用户视线有一个稳定的「进度锚点」。

### 1.2 移动端提交按钮会「无声消失」

`Workbook:99` 的页脚条件是 `(!mobileSheet || allVisited || currentActive.pending)`，而 `:100` 的进度提示 `已查看 N / M 页` 又带 `v-if="!mobileSheet"`。组合结果：**手机上，只要还没翻完所有工作表，提交按钮和进度提示同时不出现**，用户看不到任何解释。

**建议**：移动端页脚常驻，未达标时显示禁用态按钮 + 明确文案（如「还需查看 3 张表：电气 · M1变电所、M2变电所、HVDC」并可点击直达）。

**收益**：消除「找不到提交按钮」这一最容易导致巡检超时被自动收尾的阻塞点。

### 1.3 非定时模式下存在「无点击自动开轮」的隐藏路径

`Page:858-867` 的 watcher：当 `preview` 加载完成且 `selectedProfessions` 非空时，直接 `void start()`，无需用户点击。而 `refreshPreview`（`:839`）在切换楼栋时会把 `selectedProfessions` 默认设为**全部专业**。

目前 `:861` 有 `current.scheduled` 短路，定时取数上线后这条路径大概率休眠。但它是一个**未爆弹**：一旦某楼 `scheduled=false`，用户一进页面就被静默开轮，且开的是全专业。

**建议**：删除自动开轮，或至少改为「已为你预选全部专业，点击开始」的显式确认。

**收益**：开轮这个不可逆动作（后端已移除取消功能，`:1696-1697` 恒定 409）必须来自明确意图。

### 1.4 开始巡检的专业选择器信息不足且位置不当

生效的专业勾选在 `Page:32-37` 的 `#start` 插槽里，被塞进工作簿工具栏。对比死代码版本 `:74` 有 `{{ item.name }} · {{ item.count }} 台`，**生效版本 `:33` 丢掉了设备台数**。

**建议**：把「开始本轮」提升为独立的开轮卡片（专业 + 台数 + 预估工时 + 本轮时点 + 数据批次时间），确认后再进入工作簿。

**收益**：开轮前就能判断工作量与分工，而不是开轮后才发现选错——因为 `active.professions` 开轮后**后端没有任何修改入口**（`daily_inspection.py` 全量引用中无写入点），选错只能等下一轮。

## 2. 人员分工与切换

### 2.1 第二个人无法加入已开始的轮次，且界面不解释

后端 `:1670-1674`：已有 active 时 `start` 直接 409「本楼已有一次巡检，请刷新后继续。」。刷新后第二人看到的是**只含第一人专业的轮次**，另一专业的设备被 `selected_devices`（`:1044-1047`）过滤掉。他无法把自己的专业加进来，唯一出路是等这轮归档后开第 2 轮（每班仅 2 轮，`ROUNDS_PER_SHIFT=2`）。

**建议**：
- 开轮时若检测到本楼已有进行中轮次，明确展示「本轮由 X 于 HH:MM 开始，已选专业：暖通（7 台）。本班剩余 1 轮」，并提供「加入本轮」的说明性引导（即使后端暂不支持追加专业，也要把约束讲清楚，而不是丢一个 409）。
- 配套后端增加 `append-profession` 能力，允许在未确认前追加专业。

**收益**：两人分工是这个模块的核心场景，目前的失败模式是「第二个人白跑一趟 + 看到一句看不懂的报错」。

### 2.2 缺少「谁在填什么」的实时可见性

`view()`（`:1503-1536`）返回的 active **不包含 `started_by` 和 `actor`**（对比 `:1550` 写入 vs `:1519-1535` 输出）。前端只能看到事后的 `profession_confirmations[p].actor` 和 `reviews[device].actor`，没有任何在线状态、专业锁或「同事正在编辑某设备」的信号。

`resolve_duty`（`:134-139`）只返回 `{scope,date,shift,group?}`，**不含当班人员姓名**。

**建议**：
- 后端在 `view()` 暴露 `started_by` / 当前 `actor`，前端在状态层显示「本轮 · 张三 开轮 · 李四 已确认电气」；
- 增加轻量 presence（复用已有的 8 秒 `refreshSharedStatus` 轮询，`:1047`），标注「暖通 有人正在填写」；
- 按专业做**软锁提示**（不做硬锁，避免死锁）：进入某专业首张表时广播，他人看到「李四 正在填 暖通」。

**收益**：两人分工时避免重复劳动和互相覆盖；现有的冲突解决 UI（`Page:180-186`「使用共享填写 / 合并我的改动」）是事后补救，成本高且容易误判。

### 2.3 按专业签字确认的能力应当接回界面

后端 `confirm-profession` 的设计意图很清晰（`:1063-1064` 注释）：确认是对「当时看到的读数」作证，源数据刷新会让确认失效。这是一套**为分专业签字量身定做**的机制，但目前只有 `sheet_workflow` 的隐式全确认在用。

**建议**：在工作簿状态层增加专业签字条——每个已选专业一个 chip，显示「待确认 / 已确认（谁 · 何时）」，点击触发 `confirm-profession`；全部签字后提交按钮才亮起，且提交时不再走隐式全确认。

**收益**：把「两人各管一个专业」变成可追溯的责任划分，归档记录里 `开始人员` / `巡检人员` 才有真实含义。

## 3. 表格互换（本班专业归属）

### 3.1 入口藏得太深，且缺少「已调整」的可视标记

当前唯一入口是 `Workbook:108`：表格设置弹窗 → 「本班专业归属」区块 → 当前工作表的 电气/暖通 两个按钮。要互换必须先切到那张表、再打开设置弹窗。而且**界面上看不出哪张表已被改过归属**——只有专业筛选下拉和页签标签跟着变。

**建议**：
- 在工作表页签上直接标注归属徽标（`电气` / `暖通`），被本班改过的加一个「已调整」角标；
- 提供「本班专业归属」总览面板：一次列出全部工作表 + 当前归属 + 默认归属，支持批量调整与**一键恢复默认**。

**收益**：互换从「逐张点进设置」变成「一屏总览批量改」，符合开班前一次性排布的真实动作。

### 3.2 互换会作废所有专业确认，但界面完全不提示

`daily_inspection.py:1736-1737`：`sheet-group` 成功后 `review_version += 1` 且 **`profession_confirmations = {}` 全清空**。前端 `:108` 的说明只有「仅影响本楼本班次，下一班恢复默认」，**没有警告确认会被打回**。

**建议**：点击互换时若已有专业确认，弹出明确二次确认：「调整归属会使 电气、暖通 的已有确认全部作废，两人需重新确认。」

**收益**：避免「我已经确认了怎么又变回待确认」的困惑，这是最容易在交接班时引发争执的静默副作用。

### 3.3 后端没有「恢复默认」，且分组只增不减

`groups` 文档（`sheet-groups:{scope}:{date}:{shift}`）只写入不清理，没有清空接口，只能一张张点回原专业。

**建议**：后端补 `reset` 动作（或允许传默认值即删除该 key），前端提供「全部恢复默认」。

### 3.4 历史轮次看到的是「当前班次」的归属，不是该轮冻结的归属

后端已把归档时的 `sheet_groups` 写进每个 round（`:2293`、`:2298`），但前端 `Round` 类型（`Workbook:131`）**没有声明也没有使用**这个字段；顶层 `sheet_groups` 的班次取法是「active 的班次，否则当日最后一轮的班次，否则当前时钟班次」（`:2440-2441`），跨班次查看时会错位。

**建议**：查看历史轮次时消费 round 级 `sheet_groups`，展示该轮当时的真实归属。

**收益**：归档可追溯。否则事后复盘时看到的分组不是当时的分组，互换记录形同丢失。

### 3.5 无法在开轮前预排归属

`:108` 的条件是 `currentActive && !readOnly && currentPage`，即**必须已有进行中轮次**才能调整。但归属排布本质上是开班前的准备动作。

**建议**：允许在预览态（未开轮）调整并暂存为本班次预设，开轮时生效。

## 4. 单人全量巡检

### 4.1 「必须翻完所有工作表」的门槛与已选专业不一致

`Workbook:201` 的 `requiredPages = basePages`，即本楼**全部**非封面工作表；后端 `:1799-1804` 同样不按 `active.professions` 过滤。结果：**即使本轮只勾了暖通，也必须逐页翻完电气的所有表**才能提交。

这与 `workbook()` 归档时的模板过滤（`:2181-2183`，按静态专业）**口径不一致**。

**建议**：`requiredPages` 与后端校验都改为「按本轮已选专业过滤」。只巡暖通的人不应该被电气的 10 张表卡住。

**收益**：单人只做单专业时，翻页量减半以上；这是当前最容易造成巡检超时的硬门槛。

### 4.2 逐页查看进度只存在本机 localStorage，换设备即归零

`viewedKey()` / `restoreViewed()` / `markViewed()`（`Workbook:315-325`）把 visited 存在 `localStorage['inspection-viewed:{draft_key}:{round_id}']`。而工作表**排序**偏好却通过 `/api/workspace-layouts/desktop/inspection-sheets-{scope}`（`:531`、`:540`）同步到账号。

**同一组件里两套持久化策略**：排序跨设备同步，翻页进度不同步。现场常见「电脑上翻了一半，拿手机去现场继续」，进度直接归零，必须重翻全部表。

**建议**：把 visited 进度随 `submit` 之外的心跳上报后端（已有 8 秒轮询通道），或至少在切换设备时提示「本机无翻页记录，需重新逐页查看」。

**收益**：单人全量巡检往往跨设备完成，这是最实际的时间浪费点。

### 4.3 单人做两个专业时，确认会因源数据刷新而连环失效

`profession_version`（`:1062-1075`）把**实时源读数**纳入哈希。一个人先确认电气、再确认暖通，中间若 `sync_active_live` 换了批次（`:1407` bump `review_version`），电气的确认自动失效，需重做。

**建议**：确认失效时不要静默重置，明确提示「电气确认已失效：源数据在 14:03 刷新，N 台设备读数变化」并提供「只看变化项」的复核视图。

**收益**：单人全量场景下失效概率翻倍，静默重置会让人反复白确认。

## 5. 数据核对效率

### 5.1 没有「本轮 vs 上轮」的对照视图

工作簿用 `round-tabs`（`:35-40`）在四个时点间切换，同一时刻只显示一个轮次的值。历史单元格虽有 `.history-cell` 淡蓝底色（`:554`），但**无法把本轮读数和上轮读数并排比较**。

巡检核对的核心动作恰恰是「这个值和上次差多少」。

**建议**：增加「对比模式」，把上一轮同一测点的值与差值并列显示，差值超阈值高亮。数据已经在 `report.rounds` 里，纯前端即可实现。

> **实现时必须注意（原建议此处有误，已更正）**：不能按「同一单元格地址」配对。除 `暖通冷机系统巡检表` 外，其余原表是**一张表容纳 4 个轮次、每轮映射到不同的列**（`daily_inspection_original.py:145`、`:167` 用 `('白班'|'夜班')+轮次+'单元格'` 取列；catalog 路径用 `mapping['cells'][shift+round]`，`:185`）。跨轮次根本不存在「同一个 cell 地址」，按地址 join 会一条都匹配不上。
>
> 正确做法是按**语义身份** join。后端两条路径（`daily_inspection_original.py:173-190` 实时、`daily_inspection_sheet_edit.py:129-131` 归档）产出的单元格条目都带 `device` / `kind`(`point`|`section`|`paired`) / `point_id` / `parameter` / `location` / `form`，用这些字段构造 join key 即可。
>
> 另一个有利事实：`view_sheet` 单表筛选**只裁剪单元格数组，从不删轮次**（`daily_inspection.py:2366-2368`），所以一次单表请求就拿到了该表在当天 4 个轮次里的全部读数，跨轮对比无需额外请求。

**收益**：这是核对效率提升最大的一项。当前要靠来回切时点 + 人脑记忆。

### 5.2 没有「跳到下一个待填」

`moveEdit(±1)`（`:380-385`）支持 Alt+↑/↓ 在**同类**单元格间移动（`:331-337` 的 `editNeighbors` 已按 `mapped` 过滤），但没有「跳到下一个空单元格」的命令。

**建议**：增加「下一个待填」按钮 + 快捷键，并在状态层显示「本班剩余 N 个待填」。

**收益**：一张 200 格、实填 40 格的表，靠滚动找空格非常耗时。

### 5.3 缺少异常清单汇总

填 `×` 会弹出异常说明（`:119`、`:375`），逐个单元格处理。但**提交前没有任何地方能看到「本班一共几处异常、分别在哪、备注写了什么」**。

**建议**：提交前增加「本班异常汇总」抽屉，列出全部 `×` 的 表 · 单元格 · 设备 · 备注，支持点击定位、补齐空备注。

> **这一项无法纯前端实现，必须动后端。** 已核实：`view_sheet` 会把每一轮的 `original_cells` / `extra_cells` 裁剪到**只剩当前这一张表**（`daily_inspection.py:2366-2368`），所以前端手里永远只有单表数据，凑不出跨表的异常清单；而后端**不存在**任何返回单元格级 `×` 清单的轻量接口（`inspection_report()` 是唯一产出原表坐标的地方，只被 `day-sheet` / `day-export` 调用）。
>
> 现有「便宜信号」都不够用：`summary_only` 下归档轮次虽有 `abnormal` 字段，但那只是**异常设备数**、没有坐标，且进行中/待上传轮次连这个字段都没有（`:2395-2398`、`:2405-2408`）；`history-record` 的 `devices_data` 完全没有 template/sheet/cell 坐标。
>
> 推荐做法：在 `collect()` 里加一个 `abnormal_only` 分支，复用现有解析、只把 `value.strip()=='×'` 的条目放进 payload。服务端解析成本不变，传输量极小。逐表 `view_sheet` 轮询聚合是退路，但请求数等于表数。

**收益**：交接班汇报和归档复核都直接需要这份清单；也能拦住「填了 × 但备注被跳过」的情况（后端 `:1169-1170` 会 400，但报错发生在提交后）。

### 5.4 生效界面里没有搜索

死代码 `Page:127` 有「搜索设备、位置或测点」，生效的工作簿只有 `NSelect filterable`（`:20`）按**表名**搜索。找不到「某个测点在哪张表哪个格子」。

**建议**：增加全局搜索，输入测点名/设备名 → 定位到 表 + 单元格 + 高亮。

### 5.5 「缺失」只是前端引导，用户不知道后端会自动补值

后端 `finalize_reviews`（`:1157-1165`）在归档时会**用源参考值自动补齐空白参数**，全非空则 result 自动置「正常」。前端把空格标成 `待填写`（`:306`）+ `.empty-cell` 警示色，但**没有告诉用户「不填会自动采用源值并判定正常」**。

**建议**：在待填单元格 tooltip 或提交前汇总里明确：「未填写项将采用源数据 X 并计为正常」。若业务上希望缺失必须人工处理，则应推动后端补硬校验——目前前后端语义不一致。

**收益**：避免「我以为没填就会被打回，结果默默归档成正常」的责任风险。

## 6. 界面一致性

### 6.1 同一组件里混用三套颜色令牌 + 硬编码色值

`Workbook` 里同时出现：
- `var(--inspection-line)` / `var(--inspection-surface)` —— 定义在 `Page:1069-1071` 的 `.inspection-page` scoped 样式上，靠 DOM 继承生效；
- `var(--v2-palette-accent-text, var(--inspection-primary, #2457d6))` —— 其中 **`--inspection-primary` 全仓库没有定义**，永远走 fallback；
- 硬编码 hex：`#fff0b8`（当前格背景，`:244`）、`#111827`、`#ffc83d`、`#5783a9`（图例，`:554`）、`#2457d6`（多处）。

**建议**：统一收敛到 `--cf-*` 设计令牌，删除 `--inspection-primary` 这个幽灵变量，把高亮/图例色改为令牌派生（`color-mix`）。

**收益**：主题切换（深色模式、高对比度）时工作簿不会掉色；后续调色不用改十几处。

### 6.2 naive-ui 组件与原生控件混用，同类操作控件形态不统一

- 工作表切换：桌面用 `NSelect filterable`（`:20`），移动端用原生 `<button>` 页签（`:57-60`）；
- 轮次切换：原生 `<button>` + `.selected`（`:36`）；
- 专业筛选：原生 `<select data-native-select>`（`:18`）；
- 按钮：`NButton`（表格设置、排序、提交弹窗）与原生 `<button>`（刷新、导出、上一格/下一格）并存。

三个都是「切换一个视图维度」，却用了三种控件。

**建议**：确立规则——**同维度的视图切换统一用分段控件（segmented），选择类统一用 NSelect，动作类统一用 NButton**，原生 `<select>` 仅保留在移动端需要系统滚轮的场景。

### 6.3 页面 / 工作簿 / 历史三个视图视觉语言割裂

`Page` 与 `History` 共享 `.inspection-*` 命名与 naive-ui 观感；`Workbook` 是完全独立的 `.book-*` 体系（`Workbook:553-618`，65 行 CSS 压成 4 行超长单行，可读性极差）。

**建议**：抽出 `inspection.css` 共享层（间距、字号阶梯、边框、状态色、控件尺寸），三个视图共用；把 `Workbook` 的压缩 CSS 展开重构。

### 6.4 图例与保存状态挤在同一行，语义混淆

`:31-34` 的 `.book-status`：`[色块] 本次巡检 [色块] 历史巡检` 是**颜色图例**，紧接着 `正在编辑 B12` 和 `单元格修改自动保存` 是**保存状态**，中间无分隔，读起来像一句话。

**建议**：图例移到表格右上角浮层或表头旁，状态条只保留保存状态。

### 6.5 禁用态没有原因说明

楼栋下拉（`:14`）、日期（`:15`）、刷新/导出（`:16-17`）在 `saving || dirty || !!editing || !!abnormal || sortOpen` 时禁用，但**不解释为什么禁用**。用户填了一半想切楼栋，只看到灰掉的下拉。

**建议**：禁用控件加 tooltip：「有未保存修改，保存后可切换楼栋」。

## 附：建议的落地顺序

1. **先决策**（§0）：工作簿是唯一编辑面，还是「工作簿 + 卡片快速核对」双模式？这决定后面一半建议的做法。
2. **再拆门槛**（§4.1 + §1.2）：这两项是当前最容易让巡检超时被系统自动收尾的原因，改动小、收益立竿见影。
3. **然后补分工**（§2.3 + §2.1 + §3.1/3.2）：把「两人分专业各自签字」这条业务主线在界面上接通。
4. **最后提效与统一**（§5.1 对照视图、§6 一致性重构）：这两项投入较大，放在功能主线稳定之后。

## 8. 复核与实施结果

| 条目 | 当前实现 |
|---|---|
| §0 | 新旧版使用同一个工作簿处理本轮与历史巡检。移除不可达的设备卡、独立原表与历史列表入口。浏览器中已有的旧版草稿继续恢复，遇到冲突时保留本机内容供核对。 |

| §2.1–§2.3 | 同楼人员可在任何专业确认前加入未选专业。记录开轮人、最近查看的工作表、专业确认人和时间。已选专业分别确认，确认齐全后统一归档。 |

| §6.1–§6.5 | 共用巡检主题变量，规范常用动作按钮。保留手机原生输入和工作表页签。图例与保存状态分离，锁定时提示原因。 |
